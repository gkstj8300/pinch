## 2. 브랜치 전략 (Branching Strategy)

- **전략**: Trunk-based Development (TBD) 지향
- **명명**: `feature/`, `fix/`, `refactor/`, `chore/` 뒤에 설명 추가

### 2.1 세부 원칙

- **작은 단위의 브랜치:** 하나의 브랜치는 오직 하나의 티켓(기능/버그)만 해결합니다.
- **단기 생명주기:** 브랜치는 생성 후 최대 48시간 이내에 `main`으로 머지되는 것을 권장합니다.
- **피처 플래그 활용:** 완성되지 않은 기능이라도 배포가 필요하다면 피처 플래그를 사용하여 `main`에 먼저 통합합니다.

## 3. 커밋 메시지 컨벤션

### 3.1 구조

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 3.2 주요 타입

| 타입 | 설명 |
|------|------|
| `feat` | 신규 기능 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `style` | 포맷팅 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 기타 설정 |

### 3.3 작성 원칙

본문(body)은 '왜(Why)'와 '어떻게(How)' 위주로 기술한다. '무엇(What)'은 diff에 이미 드러나므로 반복하지 않는다.

---

## 4. PR 및 코드 리뷰

- **Atomic PR**: 작은 단위의 변경으로 분리하여 제출
- **Context**: 왜 바꿨는지 배경 설명 필수
- **Self-Review**: 제출 전 본인 코드에 코멘트 작성

---

## 5. 체크리스트

PR 제출 전 다음을 확인한다.

- [ ] 최신 `main` 동기화 여부
- [ ] 커밋 규칙 준수 여부
- [ ] 리뷰 가능한 적정 분량 여부
- [ ] 테스트 완료 여부
